# MuzikHub architecture

This document explains how the codebase is organised and *why*. Update it when a decision changes.

## 1. Monorepo with npm workspaces

```text
packages/shared ──► apps/api
        │
        └────────► apps/web
```

- **One `npm install`** at the root installs everything; workspaces are symlinked in `node_modules/@muzikhub/*`.
- **`packages/shared` is compiled to `dist/`** and both apps import the compiled output. This means the API's production build (`node dist/server.js`) can import it without a TypeScript loader. The cost: shared must be built before the apps — the root scripts do this for you, and `npm run dev` keeps it rebuilt in watch mode.
- Only put code in `shared` that both sides genuinely need (request/response schemas, constants). Server-only logic stays in `apps/api`; UI code stays in `apps/web`.

## 2. Shared validation with Zod

One Zod schema defines a payload's shape once and gives us:

- a **TypeScript type** (`z.infer`) for both apps, and
- **runtime validation** — the API validates incoming bodies (`middleware/validate.ts`), and the web app validates responses it receives (`lib/api.ts`).

Never rely on frontend validation alone; it is a UX convenience. The server re-validates everything.

## 3. API structure (`apps/api/src`)

```text
config/env.ts         Validates environment variables at startup (fails fast, never prints values)
lib/                  Singletons & helpers: prisma client, Better Auth instance, HttpError
middleware/           Cross-cutting concerns: error handling, validation, requireAuth
modules/<feature>/    One folder per feature
  <feature>.routes.ts   HTTP layer only: parse request, call service, send response
  <feature>.service.ts  Business logic, no Express types
  <feature>.test.ts     Vitest + Supertest
app.ts                createApp(deps): builds the Express app (no network listen)
server.ts             Starts listening; graceful shutdown
```

**Why `createApp(deps)` instead of a global `app`?** Tests import `createApp` and pass fake dependencies (e.g. a database check that always fails) without starting a server or needing a database. `server.ts` is the only file that opens a port.

**Routing.** Product endpoints are mounted under `/api/v1` (constant `API_V1_PREFIX` in shared). Better Auth owns `/api/auth/*`; it is mounted *before* `express.json()` because it parses its own request bodies.

**Errors.** Throw `HttpError(status, code, message)` anywhere; the error handler converts it to the shared `ApiError` shape `{ error: { code, message, details? } }`. Unknown errors are logged server-side and returned as a generic 500 so internals never leak. Express 5 forwards errors thrown in async handlers automatically.

## 4. Database: PostgreSQL + Prisma 7

- Schema: `apps/api/prisma/schema.prisma`. Migrations: `apps/api/prisma/migrations/` (commit these).
- Prisma 7 specifics: connection settings live in `prisma.config.ts`, the client is generated into `src/generated/prisma` (git-ignored — regenerated by `build`, `test`, and `typecheck`), and it connects through the `@prisma/adapter-pg` driver.
- **Version pin:** Prisma is pinned to `7.10.1`. npm's `latest` tag currently points at an 8.0 release candidate, and Better Auth supports Prisma ≤ 7.
- Local development uses its own container (`docker-compose.yml`, host port **5435**, bound to 127.0.0.1) so it never touches other projects' databases.

## 5. Authentication: Better Auth

- Configured in `lib/auth.ts`: email + password, plus the **username plugin** (unique, lower-cased handle; sign-in by username or email).
- Sessions live in the database and are identified by an **HTTP-only cookie** — browser JavaScript never holds a token. Passwords are hashed with **scrypt** (Better Auth's default; OWASP-acceptable, no native dependency).
- **Server-controlled fields** (`platformRole`, `status`) are declared `input: false`, so sign-up/update requests cannot set them. `primaryUse` is validated in a `user.create.before` hook.
- A `user.create.after` hook creates the user's `Profile` row, so every account has exactly one.
- **Account status** is enforced on the server in three places: a `session.create.before` hook stops suspended, banned and deactivated users from signing in (and first reinstates a suspension that has expired); `requireAuth` returns 403 `ACCOUNT_INACTIVE` for an existing session whose account has been suspended or banned; and `requireFullAccess` returns 403 `ACCOUNT_RESTRICTED` on every write route for restricted accounts. See §5e.
- **Two-factor** (`twoFactor` plugin, issuer "MuzikHub"): TOTP plus 10 single-use backup codes, both stored encrypted; 10 wrong codes lock the account for 15 minutes. "Trust this device" is rejected in `hooks.before`. Two-factor is required for staff and optional for members.
- **Password reset** revokes all other sessions. **Rate limits** apply to sign-in, sign-up and reset (disabled only under `NODE_ENV=test`).
- **Email**: see §5d (Resend). Email verification is *optional* at this stage (approved 2026-11-24).
- Two separate role concepts: `PlatformRole` (USER / MODERATOR / ADMIN — global) and, later, community roles scoped to one community. A community moderator is never a platform moderator.

## 5a. Profiles

- `Profile` (1:1 with `User`) holds bio, location, career stage, cover, onboarding progress.
- **Multiple professional identities** are a `CreativeRole[]` enum array; genres and goals are string arrays validated against the vocabularies in `packages/shared/src/taxonomy.ts`. GIN indexes make "has any of these roles/genres" discovery filters fast. A join table was considered; arrays were chosen because the role list is a fixed enum with no per-role data.
- **External links** (`ProfileLink`) are https-only, and their platform is **derived from the hostname on the server** (`detectLinkPlatform`) — a client cannot label an arbitrary URL as "Spotify". Look-alike domains (`spotify.com.evil.example`) resolve to `WEBSITE`.
- Onboarding progress (`onboardingStep`) only moves forward; completion is idempotent.

## 5b. Media (Cloudinary) — Milestone 2

**Flow:** browser asks the API to sign → browser uploads **directly** to Cloudinary (big files never pass through our server) → API **verifies** what Cloudinary stored → asset becomes READY → it can be attached to a profile, portfolio item or post.

- **Why sign on the server:** the API secret never reaches the browser, and the signature pins the exact `public_id` (`<folder>/<env>/<userId>/<assetId>`), `allowed_formats` and `overwrite=false`. A forged `public_id` is rejected by Cloudinary (401 — tested live); a replayed signature can't replace a verified file.
- **Why verify after upload:** the browser's claims (size, type) are only used for early feedback. `confirm` fetches the real resource and checks resource type, format, size and duration; rejects are deleted. Audio and video both use `resource_type=video`; a real video has width/height, audio doesn't.
- **Ownership:** `requireAttachable` checks owner + READY + purpose + kind on every attach. Unique FKs mean one file fills one slot.
- **Cleanup:** removal marks rows DELETING, then destroys in Cloudinary; failures stay DELETING and `npm run media:cleanup` retries them and removes uploads that were never confirmed or never attached (24 h). Run it on a schedule in production (e.g. Render cron).
- **Resilience (`apps/web/src/lib/upload.ts`):** XHR for real progress events; files > 20 MB go in 6 MB chunks (`X-Unique-Upload-Id` + `Content-Range`), so a dropped connection only resends one chunk; network errors retry with backoff (1 s, 2 s, 4 s); 4xx rejections don't retry; failed uploads keep the file for a one-tap Retry; Post/Publish are disabled while an upload is running.
- **Delivery:** `f_auto,q_auto` (AVIF/WebP where supported). Images: 320/640/960/1280w + 192px square avatar. Feeds and cards cap the srcset at **960w** so dense phone screens don't fetch 1280w on mobile data; detail pages may use 1280w. Audio is transcoded to 128 kbps MP3 with `preload="none"`. Video shows a poster only and loads on tap; nothing autoplays.
- **Provider boundary:** modules depend on the `MediaStorage` interface (`lib/media-storage.ts`); tests use an in-memory fake, and an opt-in live suite (`CLOUDINARY_LIVE=1`) exercises the real account.

## 5c. Feed, discovery and relationships — Milestone 2

- **Feed ranking** is deliberately simple (CLAUDE.md §8.4): *Discover* = every visible post newest-first (useful with few users); *Following* = people you follow + you. Cursor pagination on (createdAt, id).
- **One visibility rule** (`visiblePost`): author ACTIVE, and showcased work still published + public. Archiving or privatising work removes it from the feed automatically.
- **Follow vs connect** are separate tables and endpoints. Connection state changes use conditional `updateMany` (e.g. "accept only if still PENDING and you are the addressee"), so double clicks and races can't create invalid states; the partial unique index is the final guard.
- **Discovery** queries real rows with Prisma: case-insensitive text on name/username/bio/location, exact skill match, `hasSome` on GIN-indexed role/genre arrays. At larger scale, add `pg_trgm` indexes for fuzzy text search.
- **Frontend:** TanStack `useInfiniteQuery` + an IntersectionObserver sentinel with a "Load more" fallback; likes are optimistic with rollback; filters live in the URL.

## 5d. Transactional email — Resend (confirmed 2026-11-24)

```text
Better Auth hook (sendResetPassword / sendVerificationEmail)
  → email-templates.ts   (escaped HTML + plain text)
  → mailer.sendEmail     (per-recipient limit: 3 per kind per hour)
  → transport            capture (tests) | console (dev) | resend (production)
```

- **One mailer**, three transports chosen by `EMAIL_TRANSPORT` (defaults: test → capture, development → console, production → resend). In development you can opt in with `EMAIL_TRANSPORT=resend`, which requires `RESEND_API_KEY` and `EMAIL_FROM`.
- **Production refuses to start** without `RESEND_API_KEY` (must start with `re_`) and `EMAIL_FROM`. Before this change, a production reset request silently sent nothing.
- **Resend SDK** (`resend` 6.x): `emails.send(payload, { idempotencyKey })`. It returns `{ data, error }` rather than throwing. Errors become `EmailDeliveryError(code)`, and logs contain only Resend's error code and a masked recipient (`ay***@domain`), never the key, the provider's message, the content or the link.
- **Idempotency key** = hash of the one-time token, so a retried send of the *same* link goes out once.
- **No account probing:** Better Auth catches send errors and returns the same response either way. The per-recipient limit also returns silently.
- **Tokens (Better Auth, unchanged):** reset tokens are single-use (atomically consumed) and expire after 1 hour; reset revokes other sessions. Verification tokens are signed JWTs that expire after 1 hour; reuse within that hour is harmless.
- **Verification return flow:** the server rewrites the link's `callbackURL` to `WEB_APP_URL/email-verified`, so it always lands in the web app (`?error=…` for invalid or expired links). The web app shows a banner with a **Resend** action (60-second cooldown) to unverified users.
- **Limits:** the per-recipient limit is in memory, which is fine for one API instance; move it to the database or Redis if the API scales out. Better Auth's per-IP limits also apply.

**Current state of the Resend account (checked 2026-11-24):** the API key is valid, and **0 sending domains** are configured. Until a domain is verified, production email cannot go to real recipients. The opt-in live test uses Resend's documented test sender with the `delivered@resend.dev` sink.

**To enable production email (pending):**
1. In Resend → Domains, add a subdomain you control (e.g. `mail.<your-domain>`).
2. Add the DKIM and SPF DNS records exactly as shown (MX/TXT/CNAME; don't proxy CNAMEs through Cloudflare). Verification usually takes about 15 minutes and can take up to 72 hours. Then add a DMARC record.
3. On Render, set `RESEND_API_KEY` (preferably a sending-only key) and `EMAIL_FROM="MuzikHub <no-reply@mail.<your-domain>>"`.

Free plan (resend.com/pricing, checked 2026-11-24): 100 emails per day, 3,000 per month, 3 domains, 10 requests per second per team. Test sends count against the quota.

## 5e. Admin Console (approved and implemented 2026-11-24)

**Where it lives.** API: `modules/admin/` (`admin.routes.ts`, `users.service.ts`, `reports.service.ts`, `moderation.service.ts`, `overview.service.ts`, `bootstrap.ts`), `middleware/require-staff.ts`, `lib/audit.ts`, `lib/account-status.ts`, `lib/rate-limit.ts`. Shared: `packages/shared/src/admin.ts`. Web: `features/admin/*`, lazy-loaded under `/admin`.

**Permission model.** `packages/shared/src/admin.ts` holds the single matrix (`PERMISSIONS`, `can(role, permission)`), which both the API and the UI read. The UI uses it only to hide controls; **every check happens on the server**. Rules applied in the services:
- `ROLE_RANK` (USER < MODERATOR < ADMIN): staff can act only on accounts of a **lower** rank, and never on their own account.
- Suspensions need a reason and an end date, capped by `SUSPENSION_MAX_DAYS` (MODERATOR 30 days, ADMIN 365). Bans, ban reinstatements, role changes and two-factor resets are ADMIN-only.
- Role changes run in a **serializable** transaction. They refuse self-changes, require the target to be active and verified before it gets a staff role, and refuse to demote the last ADMIN (`LAST_ADMIN`). A write conflict between two concurrent transactions returns 409 `CONFLICT_RETRY` rather than 500.
- Moderators never receive email addresses (`users.viewPrivate`), and escalated reports can only be decided by an ADMIN.
- Resources are looked up by id **and** the rules above, so changing an id in a request (IDOR) gains nothing.

**Request pipeline.** `GET /api/v1/admin/me` works before two-factor is set up, so the UI can show enrolment. Every other admin route passes through `requireAuth` → `requireStaff` (which re-reads role, status and `twoFactorEnabled` from the database on each request and returns `NOT_STAFF`, `ACCOUNT_RESTRICTED` or `TWO_FACTOR_REQUIRED`) → per-route `requirePermission` → Zod validation → a rate limit (`adminReadLimit` and `adminWriteLimit`, both in memory) → the service. Sensitive actions also call `assertFreshSession` (the session must be under `FRESH_SESSION_MINUTES` = 15 old, otherwise `REAUTH_REQUIRED`).

**Account states.** `ACTIVE` · `RESTRICTED` (still visible; can read but every write route refuses) · `SUSPENDED` (hidden, sessions deleted, `statusUntil` required; a 5-minute sweep in `server.ts` and the sign-in hook reinstate it at expiry and record a `system:suspension-expiry` audit entry) · `BANNED` (hidden, sessions deleted, ADMIN-only reinstatement) · `DEACTIVATED`. `visibleUser` / `isVisibleStatus` (ACTIVE or RESTRICTED) replaced the old `status: 'ACTIVE'` filters in the feed, discovery, network, profile and portfolio queries.

**Moderation.** Posts, comments and portfolio items are **soft-removed** (`removedAt`, `removedById`, `removalReason`). They disappear from every public query and count, the owner sees a notice on their own portfolio item, and staff can restore them. Removing a profile photo or cover deletes the Cloudinary asset, so it cannot be restored. Content owned by staff of the same or a higher rank is protected.

**Reports.** Statuses are `PENDING → UNDER_REVIEW → RESOLVED | DISMISSED`, with an assignee, an `escalated` flag, internal `ReportNote`s, and a resolution text and resolver. Open reports are listed with escalated ones first. Closing a report can also close the other open reports on the same target (`includeRelated`). Every transition is a conditional update, so two moderators cannot close the same report twice.

**Audit log.** The `audit_log` table has no foreign key on `actorId`, so entries survive account deletion. Each entry stores `actorRole` and `actorLabel` (for CLI and system actors), `action`, `targetType` and `targetId`, `reason`, `before` and `after` JSON, and `ipAddress`. Every admin write calls `writeAudit` inside the same transaction as the change. **Append-only at the database level:** the trigger function `audit_log_is_append_only()` rejects `UPDATE` and `DELETE` (row trigger) and `TRUNCATE` (statement trigger). The only exception is a `TRUNCATE` inside a transaction that first runs `set_config('muzikhub.allow_audit_truncate','on',true)`, which the test reset uses. The database owner can still drop the triggers; for stronger guarantees in production, run the API as a role that does not own the table.

**First administrator and recovery (CLI only).** `npm run admin:grant-initial -w @muzikhub/api -- --email <email>` (or with no argument, which prompts for the email). The account must exist, have a verified email and be active. The command refuses if any ADMIN already exists, makes no change if the account is already an admin, runs in a serializable transaction and writes an audit entry as `cli:admin:grant-initial`. It exits with 1 on refusal. `npm run admin:reset-two-factor -w @muzikhub/api` is the last-resort recovery when a staff member has lost both their authenticator and their backup codes; it asks for a reason, asks for confirmation and is audited. No HTTP route can create the first administrator.

**Migration.** `20261124005215_admin_console_foundation` renames the `ReportStatus` values in place (`OPEN→PENDING`, `ACTIONED→RESOLVED`, adds `UNDER_REVIEW`) instead of using Prisma's drop-and-recreate, which would have failed on existing rows. It was tested on a copy of the database containing legacy rows. It has been applied to the local dev and test databases only, **not to production**.

**Deferred.** `FINANCE_ADMIN` and finance views (with payments); announcements (a disabled "Pending" nav entry); community, competition and opportunity oversight (with those pillars). The overview lists these as pending rather than showing placeholder numbers.

## 5f. Foundation (M0, 2026-11-24)

**Request pipeline for `/api/v1`:**
1. Helmet, CORS (allow-list).
2. `express.json` (1 MB).
3. **`originCheck`** (CSRF): for unsafe methods, an `Origin` must be in `CORS_ORIGINS`, else `Sec-Fetch-Site` must be same-origin or none; otherwise `403 CROSS_ORIGIN_REJECTED`. This layers on top of SameSite=Lax cookies.
4. Per route: `requireAuth` → **rate limit** → `requireFullAccess` → `requireVerifiedEmail` (when the flag is on) → `validateBody` → **`idempotent()`** → handler.

**Errors:** RFC 9457 problem details (`application/problem+json`): `type` (stable URN), `title`, `status`, `detail`, `code`, `instance`, `errors`. See `lib/problem.ts`, `problemSchema` in shared, and `docs/migrations/2026-11-rfc9457-errors.md`.

**Rate limits** (`lib/rate-limit.ts`; per user, in memory, 429 + `Retry-After`):

| Class | Limit | Routes |
|---|---|---|
| content-write | 20/min and 200/h | create/edit post, comment, create/edit/publish portfolio |
| reaction | 60/min | like/unlike, follow/unfollow |
| connection-request | 30/h | send connection request |
| report | 20/h | report content |
| upload | 60/h | start upload |
| admin-read / admin-write | 240/min / 60/min | Admin Console |

Better Auth limits sign-in, sign-up and reset separately.

**Passwords:** scrypt N=2^17, r=8, p=1 in `$scrypt$…` format, with rehash-on-sign-in of Better Auth's older hashes and at most 2 concurrent hashes. See `lib/password.ts` and ADR 0001.

**Email verification flag:** `REQUIRE_EMAIL_VERIFICATION` (default false). When true, posting, commenting and publishing work need a verified email.

**Idempotency and outbox** (ADR 0003):
- `idempotency_key` replays the first response for a repeated key and refuses reuse with a different request.
- `outbox_event` is written in the caller's transaction; a worker in `server.ts` delivers it every 2 s with `SKIP LOCKED`, backoff and give-up.
- Migration `20261124063925_reliability_idempotency_outbox` is applied to local dev and test only. **Supabase not migrated** (needs approval).

**OpenAPI 3.1:** `openapi/operations.ts` lists every operation and `document.ts` builds the spec, served at `GET /api/v1/openapi.json`. A drift test reads the real route table, so an undocumented or invented operation fails CI.

**Tooling** (ADR 0002): Prettier (`npm run format`), Oxlint plus the token guard (`npm run lint`), Lighthouse CI (`lighthouserc.json`) and `scripts/js-budget.mjs`.

**CI** (`.github/workflows/ci.yml`) has five jobs:
- quality;
- test, against PostgreSQL 18;
- e2e: the Cloudinary journeys skip with a reason without repository secrets;
- performance: API + preview, JS budget, Lighthouse;
- security: audit-ci with a reviewed allow-list, gitleaks over history with a reviewed `.gitleaksignore`, and dependency review on PRs.

## 6. Payments: Notch Pay (not implemented)

Only environment variables exist (`NOTCHPAY_*`, server-side, optional). When the payments module is built it must:

1. Create payments from the API (never from the browser with a private key).
2. Treat the browser redirect/callback as a hint only.
3. Confirm payment status server-side (webhook with signature verification and/or a status lookup via the Notch Pay API) **before** activating anything paid.

## 7. Frontend (`apps/web`)

- React 19 + Vite + Tailwind CSS v4 + shadcn/ui, **React Router 7**, **TanStack Query** (server state), **React Hook Form + Zod** (forms, using the shared schemas).
- Layout: `src/components/layout` (AppShell: top bar, sidebar, mobile bottom nav), `src/components/ui` (design-system primitives), `src/features/<area>` (pages + feature components), `src/lib` (API client, auth client, query hooks).
- **Design system** = the approved prototype (`~/Downloads/index.html`). Its exact hex values are the tokens in `src/index.css` (dark-only, Inter). Primitives in `components/ui/primitives.tsx` mirror the prototype's classes (`Eyebrow`, `PageHeader`, `Panel`, `Pill`, `ToggleChip`, `Hint`). Use them rather than restyling ad hoc.
- **Navigation honesty:** unbuilt areas appear in a "Coming soon" sidebar group and as disabled mobile tabs — never as dead links. Add `to` in `navigation.ts` when a feature ships.
- **API client** (`lib/api.ts`): one `request()` function — sends the cookie, maps network failures to a friendly `NETWORK_ERROR`, turns error bodies into `ApiRequestError`, and validates responses with the shared Zod schemas.
- **Route guards** are UX only; the API's 401/403 is the real protection. Post-login `?next=` redirects accept only same-site relative paths (no open redirect).
- Queries retry network blips but never 4xx; **mutations are never auto-retried** (avoids duplicate writes). Sign-out clears the whole query cache so no data from one account leaks to the next.
- Secrets never go in the frontend: only `VITE_*` variables are exposed to the browser, and none are secrets.

### Design system: olive-black and lime (approved 2026-11-24)

- **One-file palette:** `src/styles/palette.css` holds every colour value. `src/index.css` maps them to roles (`surface-footer/base/raised/overlay/chip/control`, `signal` (+hover/press), `on-signal`, `text-1/2/3`, `paper`, `on-paper(-2)`, `hairline(-strong)`, `control-border`, `danger/warning/success`) and defines the type scale (`text-display`, `h1`–`h3`, `lead`, `body`, `small`, `caption`, `label`, fluid via `clamp()`), spacing (`section`, `gutter`, `hero-top`), containers (`content` 1200 px, `wide` 1440 px, `measure` 40 rem), radii (`s` 8, `m` 16, `media` 30, pills `rounded-full`), elevation (`shadow-e1..e3`) and motion (`--motion-micro/standard/reveal`, `ease-enter/exit`). `src/design/tokens.ts` names them for TypeScript.
- **No legacy aliases:** M0 converted every colour in the app (323 values in 34 files) and removed the `forest-*`/`emerald`/`mint`/`sage` aliases. `npm run lint` runs `scripts/check-tokens.mjs`, which fails on any raw colour or one-off pixel size in web components (ADR 0002). Exceptions: the 2FA QR code sits on `bg-white` (scanners need maximum contrast). Profile-link icons are the platforms' real logo shapes (`simple-icons`, CLAUDE.md §6.2) drawn in the current text colour; they carry no brand colours, so no exception is needed.
- **`cn()`** is `src/lib/cn.ts`, configured with the type-scale names. The stock merger treated `text-h2` as a colour and silently dropped it when a colour class was present.
- **Font:** Inter Variable (already self-hosted; latin subset 47 kB woff2) for body and display, with a metric-matched Arial fallback (`size-adjust`, ascent/descent overrides) so the swap doesn't shift layout.

### Landing page (2026-11-24)

- `src/features/landing/`: `content.ts` (all copy), `LandingPage`, `LandingHeader` (fixed header that becomes solid after 16 px; scroll-spy pill nav; native `<dialog>` menu sheet with a focus wrap, Escape, scroll lock and focus return), `Hero`, `BelowFold` + `sections.tsx` (paper problem section, sticky value list, WAI-ARIA tabs, timeline, bento, trust, roadmap, accordion FAQ, lime CTA band), `previews.tsx` (illustrative UI fragments: one `role="img"` each, fictional names, labelled), `LandingFooter`, `hooks.ts`.
- **No photographs** (CLAUDE.md §20.6). The originals moved to `brand-originals/landing/` (git-ignored, outside `public/`). The LCP element is hero text.
- **Light first load:** the landing page never loads Zod, the schemas, the API client or the auth client. The signed-in check is a plain `get-session` fetch (200 + null when signed out, so no 401 in the console), and `/me` is asked only when someone is signed in. The app shell and auth guards are lazy, and `ApiRequestError` lives in `lib/api-error.ts`. Everything below the hero is a 3.6 kB chunk rendered in a transition after the hero paints.
- **Signed-in visitors** stay on the landing page and see "Open app" (`/home`, or `/onboarding` if onboarding isn't finished). Previously they were redirected.
- **SEO:** title and description (React 19 hoists them into `<head>`), static Open Graph, Twitter and Organization JSON-LD in `index.html`, `robots.txt` at build, `sitemap.xml` and canonical only when `VITE_SITE_URL` is set. Draft pages are `noindex`.
- **Pre-rendering** is not set up: this is a client-rendered SPA. The cheapest way is a ~60-line post-build script with `react-dom/server` (`prerender` of `<LandingPage>` inside a static router) that writes the HTML into `dist/index.html`, plus switching `createRoot` to `hydrateRoot` for `/`. No new dependency is needed. Moving to React Router framework mode with `prerender: ['/']` would also work, but it restructures routing.

### Supabase Free plan — limits relevant to MuzikHub

Verified on supabase.com/pricing and supabase.com/docs (billing, backups, compute-and-disk, pooling pages), 2026-11-24:

| Limit | Free plan |
|---|---|
| Inactivity pausing | Paused after **1 week** of inactivity (paid plans: never) |
| Database size | **500 MB** per project |
| File storage | 1 GB (MuzikHub stores media in Cloudinary, not Supabase Storage) |
| Egress | 5 GB, plus 5 GB cached |
| Active projects | 2 (paused projects don't count) |
| Compute | Nano: shared CPU, up to 0.5 GB RAM |
| Connections | 60 direct, 200 pooler clients (default pool size 15) |
| Backups | **No automatic daily backups and no point-in-time recovery** |

**Not confirmed on official pages:** the exact unpausing procedure, whether data is guaranteed while paused, and behaviour when the 500 MB limit is exceeded. Treat these as unknown.

**Hackathon backup practice** (Supabase's own recommendation for Free projects): export regularly with `supabase db dump` or `pg_dump`, and keep the files off-site:

```bash
pg_dump "$SUPABASE_SESSION_POOLER_URL" --format=custom --no-owner --file=muzikhub-$(date +%F).dump
```

To avoid pausing during the hackathon, keep the project in regular use; the health check `GET /api/v1/health` queries the database.

## 8. Environment variables

`.env.example` (root) documents every variable. Real values go in `apps/api/.env`, which is git-ignored. The API validates them on startup (`config/env.ts`) and refuses to start with a clear message if one is missing or malformed.

## 9. Known issues

- Route-level code splitting (Milestone 2) brought the entry bundle from 645 kB to 334 kB (104 kB gzipped); each page loads as its own chunk.

- The admin rate limits (like Better Auth's) are kept in memory: correct for a single API instance, but they reset on restart. A shared store is needed before running more than one instance.
- The audit-log triggers protect against application bugs and accidental writes, not against the database owner (see §5e).
- `npm audit` reports 3 high-severity findings in the `effect` library used by the **Prisma CLI** (`@prisma/config`). It is a development-time tool, not part of the running API. The automatic "fix" would downgrade to Prisma 6; revisit when Prisma publishes a patched 7.x.
- npm 11 blocks dependency install scripts by default; `package.json → allowScripts` approves exactly the three that are required (`prisma`, `@prisma/engines`, `esbuild`). If you upgrade those packages, re-approve with `npm install-scripts approve <pkg>`.
